# ГИА — тестирование студентов медицинского колледжа

Django-приложение для проведения первого этапа итоговой аттестации студентов
медицинского колледжа. Администратор ведёт специальности, группы и студентов,
загружает вопросы тестов из XLSX, печатает раздатки с логинами и паролями.

> Проект разработан при поддержке [chat.deepseek.com](https://chat.deepseek.com).

## Требования

- **Linux** (Ubuntu 22.04+ / Debian 12+) или **WSL2** на Windows.
  На Windows без WSL не тестировалось: команды ниже — для bash.
- **Python 3.12+** (проект разработан на 3.14).
- **Git**.
- **LibreOffice** или **Microsoft Excel** — для открытия XLSX-файлов (раздатки, шаблоны, выгрузки вопросов).

## Установка

```bash
git clone https://github.com/jdoe058/gia.git
cd gia

# Виртуальное окружение
python -m venv .venv
source .venv/bin/activate

# Зависимости
pip install -r requirements.txt

# Настройки (скопируйте шаблон и отредактируйте)
cp .env.example .env
```

В `.env` замените `SECRET_KEY` на свой. Сгенерировать:

```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

Примените миграции и загрузите стартовые данные:

```bash
python manage.py migrate
python manage.py loaddata specialties
python manage.py createsuperuser
```

> **Перед первым экспериментом в админке** сделайте бэкап пустой БД —
> точку «чистого старта». Если что-то пойдёт не так на этапе настройки,
> вернётесь к ней:
>
> ```bash
> mkdir -p backups
> sqlite3 db.sqlite3 ".backup 'backups/db_initial.sqlite3'"
> ```
>
> Как делать регулярные бэкапы — см. раздел «Данные и резервное копирование».

## Запуск

```bash
python manage.py runserver
```

- Приложение: http://127.0.0.1:8000/
- Админка: http://127.0.0.1:8000/admin/

## Возможности

- **Специальности** — справочник (6 СПО, загружаются фикстурой).
- **Группы и студенты** — администратор заводит через админку.
  Логины и пароли генерируются автоматически, печатается раздатка в XLSX.
- **Вопросы тестов** — импорт/экспорт XLSX на странице специальности.
- Вход студентов — **в разработке**.

## Данные и резервное копирование

### Что где лежит

| Что          | Где                 | Что внутри                                                  | В git                    |
| ------------ | ------------------- | ----------------------------------------------------------- | ------------------------ |
| `db.sqlite3` | корень проекта      | Студенты, группы, вопросы, ответы, пользователи             | **Нет** (в `.gitignore`) |
| `.env`       | корень проекта      | `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`                      | **Нет** (в `.gitignore`) |
| `examples/`  | папка в репозитории | Выгрузка вопросов по специальностям в XLSX                  | **Да**                   |

`db.sqlite3` — единственное место, где живут студенты, группы и пользователи.
`examples/` содержит **только вопросы** и восстанавливается через импорт на странице
специальности. Потеря `examples/` восстанавливается из git-истории; потеря
`db.sqlite3` — только из бэкапа.

`.env` терять нельзя: без `SECRET_KEY` сломаются сессии и часть криптографии.
Храните копию `.env` в надёжном месте.

### Полный бэкап БД

`cp db.sqlite3 backup.sqlite3` работает, но при активном `runserver` может дать
неконсистентную копию (WAL, незакоммиченные транзакции). Правильный способ —
через `sqlite3 .backup`, без остановки сервера:

```bash
mkdir -p backups
sqlite3 db.sqlite3 ".backup 'backups/db_$(date +%Y%m%d_%H%M).sqlite3'"
```

Альтернатива (SQLite 3.27+, компактнее):

```bash
sqlite3 db.sqlite3 "VACUUM INTO 'backups/db_$(date +%Y%m%d_%H%M).sqlite3'"
```

Оба способа создают консистентный снимок. Для полной гарантии на старых
SQLite — остановите `runserver` (`Ctrl+C`) и сделайте `cp`.

### Когда делать бэкап

- **Перед `python manage.py migrate`** — особенно на структурных миграциях
  (`RemoveField`, `AlterField`). Откат миграции — не всегда возможен.
- **Перед импортом студентов или вопросов** — импорт в непустую
  специальность/группу запрещён, поэтому для обновления данных
  администратор сначала удаляет текущие. Если новый файл окажется
  с ошибкой — импорт откатится, но старые данные уже потеряны.
- **Перед удалением группы** — удаление группы каскадно удаляет всех её
  студентов и связанных `User`.
- **Перед экспериментами в админке** — «а что если я поменяю это поле».
- **Периодически**, когда данные начнут накапливаться (результаты
  тестирования — в будущем).

### Восстановление

```bash
# 1. Остановить runserver (Ctrl+C)

# 2. Сохранить текущий файл — вдруг бэкап окажется старее
mv db.sqlite3 db.sqlite3.broken

# 3. Восстановить
cp backups/db_20261031_1430.sqlite3 db.sqlite3

# 4. Проверить, что всё на месте
python manage.py check
python manage.py shell -c "
from main.models import Specialty, Student, Question
print('Specialties:', Specialty.objects.count())
print('Students:', Student.objects.count())
print('Questions:', Question.objects.count())
"

# 5. Запустить
python manage.py runserver
```

Если после шага 4 числа не сходятся или `check` ругается — верните
`db.sqlite3.broken` на место и разбирайтесь, что не так с бэкапом.

### Что **не** является бэкапом

- **`git`** — `db.sqlite3` в `.gitignore`, история репозитория БД не хранит.
  Git — бэкап кода и `examples/`, но не данных.
- **`manage.py dumpdata`** — JSON-дамп не восстанавливает всё (некоторые
  метаданные теряются, медленно на больших объёмах, не всегда
  восстанавливаются пароли пользователей). Для переноса между СУБД — да,
  для бэкапа — нет.
- **`examples/`** — только вопросы. Студентов, групп, пользователей там нет.
- **`.venv/`, `__pycache__/`, `.pytest_cache/`** — восстанавливаются из
  `requirements.txt` и повторного запуска, бэкапить не нужно.

### Проверка бэкапа

Бэкап, который никогда не восстанавливали, может оказаться битым — узнаете
об этом в худший момент. Раз в месяц (или после важных изменений):

```bash
cp backups/db_20261031_1430.sqlite3 /tmp/db_check.sqlite3
cd /tmp && sqlite3 db_check.sqlite3 ".tables" && sqlite3 db_check.sqlite3 "SELECT COUNT(*) FROM main_student;"
```

Если таблицы и счётчики читаются — бэкап живой. Если `sqlite3` ругается на
повреждение — делайте новый бэкап и разбирайтесь, что пошло не так.

### Автоматизация (опционально)

Для учебного проекта не обязательно, но если данные станут ценными — `cron`
раз в сутки с ротацией 30 дней:

```bash
# crontab -e
0 3 * * * cd /home/eugene/gia && mkdir -p backups && sqlite3 db.sqlite3 ".backup 'backups/db_$(date +\%Y\%m\%d).sqlite3'" && find backups/ -name "db_*.sqlite3" -mtime +30 -delete
```

## Troubleshooting

### `sqlite3: command not found`

Утилита `sqlite3` нужна для бэкапов (раздел «Данные и резервное копирование»).
Установка:

```bash
sudo apt install sqlite3
```

### Permission denied: db.sqlite3

Файл принадлежит другому пользователю. Проверьте владельца:

```bash
ls -l db.sqlite3
```
Если запускаете от www-data или другого пользователя — передайте файл:

```bash
sudo chown youruser:youruser db.sqlite3
```

### Address already in use

Порт 8000 занят (возможно, старый runserver не остановился). Запустите на другом порту:

```bash
python manage.py runserver 8001
```
